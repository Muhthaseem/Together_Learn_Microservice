Service Discovery — Netflix Eureka
~3 minutes
URL to Open
http://localhost:8761 — Eureka Dashboard (no login required)

Step-by-Step Demo

  1. Open http://localhost:8761 in browser — show the Eureka dashboard
  2. Point to "Instances currently registered with Eureka" — all 10 services listed
  3. Show instance status: UP (1) for each service
  4. Run terminal command alongside: 
    docker logs tl-discovery --tail 20
    This shows heartbeat logs proving services actively check in
  5. REST endpoint to show it's a proper API: 
    curl -H "Accept: application/json" http://localhost:8761/eureka/apps
What to say

"This is Netflix Eureka — our service registry. Every microservice registers itself on startup with its IP and port. The API Gateway never has a hardcoded URL — it resolves lb://USER-SERVICE dynamically from this registry at request time. If a service crashes and comes back up, it re-registers automatically. If we spin up 3 instances of user-service, Eureka load-balances across all three with Round-Robin. This is client-side service discovery — the caller (gateway) resolves the address, not a central load balancer."

Key Point to Emphasize
"No hardcoded IPs anywhere in our code. This is what makes horizontal scaling possible — spin up more instances and Eureka automatically includes them in routing."

API Gateway — JWT Auth, Rate Limiting, Circuit Breakers
~4 minutes
Gateway Entry Point
All client traffic enters at http://localhost:8080

Demo 1 — Show JWT Validation (call without token)

curl http://localhost:8080/api/groups

Expected: 401 Unauthorized — gateway blocks unauthenticated access

Demo 2 — Show with fake token

curl -H "Authorization: Bearer fakejwt.fake.fake" http://localhost:8080/api/groups

Expected: 401 Unauthorized — signature validation fails

Demo 3 — Login and use real JWT

# Login first
$r = Invoke-RestMethod -Uri "http://localhost:8080/api/auth/login" `
  -Method POST -ContentType "application/json" `
  -Body '{"email":"your@email.com","password":"yourpassword"}'
$token = $r.token

# Authenticated call — works
curl -H "Authorization: Bearer $token" http://localhost:8080/api/groups

Gateway Filter Chain

FilterOrderWhat It Does
JwtAuthFilter-1 (first)Validates JWT signature. Checks Redis blacklist (jwt:blacklist:{jti}). Injects X-User-Id, X-User-Role headers. Skips /api/auth/** paths.
RateLimitFilter0Auth endpoints: 10 req/min/IP. Authenticated users: 300 req/min/userId. Anonymous: 30 req/min/IP. Uses Redis INCR + EXPIRE.
LoggingFilter1 (last)Logs method, path, userId, status code, and response duration.
CircuitBreakerPer-routeResilience4j: 10-call window, 50% failure → open 30s. Returns 503 JSON from FallbackController.
What to say

"The gateway validates the JWT, checks Redis to see if the token was revoked (logout blacklist), then strips the Authorization header and injects X-User-Id, X-User-Role as trusted HTTP headers. Downstream services read these headers directly — they never re-validate the token. This means zero cryptographic overhead on every service request. The circuit breaker prevents cascading failures — if user-service is degraded, the circuit opens and the gateway immediately returns 503 instead of queuing thousands of failing requests."

Async Event-Driven Architecture — RabbitMQ
~4 minutes
URLs to Show
RabbitMQ Management UI: http://localhost:15672 — Login: tl / tl_password

What to Show in the UI

  1. Overview tab — live message rate graphs, connections
  2. Exchanges tab — show tl.events (topic type, durable)
  3. Queues tab — show tl.notifications and tl.notifications.dlq
  4. Run terminal command: 
    docker exec tl-rabbitmq rabbitmqctl list_queues name messages consumers

Event Flow Architecture

[Group Service] publishes "GROUP_JOIN" [Q&A Service] publishes "QUESTION_ANSWERED" [Peer Service] publishes "SESSION_SCHEDULED" ↓ rabbitTemplate.convertAndSend("tl.events", "notification.group", payload) ↓ [tl.events topic exchange] (durable) ↓ Binding: routing key "notification.#" ↓ [tl.notifications queue] (durable, persistent messages) ↓ [Notification Service @RabbitListener] → Persist to notification_db → INCR notif:unread:{recipientId} in Redis ↓ [On failure after 3 retries, 3s backoff] ↓ [tl.notifications.dlq] (dead-letter queue for inspection)

Event Types Published

EventPublisherRouting KeyTrigger
GROUP_JOINgroup-servicenotification.groupUser joins a study group
GROUP_CREATEDgroup-servicenotification.groupNew study group created
QUESTION_ANSWEREDqa-servicenotification.qaAnswer posted to question
PEER_ACCEPTEDpeer-servicenotification.peerTutor application accepted
SESSION_SCHEDULEDpeer-servicenotification.peerTutoring session confirmed
What to say

"When a user joins a study group, the Group Service publishes an event to the tl.events topic exchange. It has no idea that a Notification Service exists — it just fires and forgets. If the Notification Service is down, RabbitMQ queues the messages — they deliver when it recovers. No notifications lost. That's temporal decoupling. We also have a dead-letter queue — after 3 retry attempts with 3-second backoff, failed messages go to the DLQ for manual inspection."

Real-Time Chat — WebSocket + STOMP
~2 minutes
URL to Open
http://localhost:3000 — Login, navigate to a Study Group, open Chat

Live Demo Steps

  1. Open http://localhost:3000 in Chrome — log in as User A
  2. Navigate to Study Groups → join or open a group → open Chat
  3. Open a second browser window (incognito) — log in as User B
  4. Join the same group → open Chat
  5. Send a message from User A — watch it appear instantly in User B's window

WebSocket Architecture

Browser (Next.js) ↓ WebSocket Upgrade: GET /ws/groups/{groupId}?token={jwt} ↓ (NOTE: browsers cannot send Authorization headers on WS upgrade) API Gateway — JwtAuthFilter extracts & validates ?token query param ↓ Chat Service (StompEndpointRegistry at /ws) ↓ @MessageMapping("/chat/{groupId}/send") → Persist message to chat_db → Broadcast to /topic/group/{groupId} ↓ All subscribers (open browser tabs) receive message instantly
What to say

"Group chat uses WebSocket with STOMP over SockJS. When a user sends a message, it's persisted to chat_db and broadcast to all subscribers on /topic/group/{groupId}. There's a subtle distributed systems problem here: browsers cannot send custom HTTP headers during a WebSocket upgrade request. So instead of the standard Authorization: Bearer header, the JWT is passed as ?token= in the query string. The gateway intercepts this and validates it identically to the header case. SockJS also provides an HTTP long-polling fallback if native WebSocket isn't available."

Distributed Tracing — Zipkin
~3 minutes
URL to Open
http://localhost:9411 — No login required

Step-by-Step Demo

  1. Open Zipkin UI at http://localhost:9411
  2. Click "Run Query" — shows recent traces across all services
  3. Click any trace — shows the waterfall diagram with parent-child spans
  4. Find a login trace — shows: Gateway → User Service → Redis → PostgreSQL
  5. Show the latency at each hop: how long JWT validation took, DB query time, etc.
  6. Click "Dependencies" tab — shows service-to-service call graph

How Tracing Works

Client Request → API Gateway ↓ Micrometer Brave creates root span with unique traceId ↓ Propagates via: X-B3-TraceId, X-B3-SpanId headers Gateway → User Service (child span) ↓ User Service → Redis (child span) ↓ User Service → PostgreSQL (child span) ↓ User Service → returns to Gateway All spans sent to Zipkin via HTTP: http://zipkin:9411/api/v2/spans Zipkin UI shows: traceId: abc123def456 ├── Gateway [0ms → 145ms] │ └── User Service [5ms → 140ms] │ ├── Redis check [5ms → 8ms] │ └── DB query [10ms → 95ms]
What to say

"Every request across our 10 services gets a unique traceId that propagates through all hops via Micrometer Brave. We run 100% trace sampling in development. This trace shows a login request: the gateway received it, forwarded to user-service, user-service checked Redis for a cached profile, queried PostgreSQL, issued a JWT, and responded — all visible as parent-child spans with exact latencies. In a traditional monolith, debugging a slow request is easy. In microservices, without distributed tracing, you're completely blind to where time is spent."

Log Flow

Each Spring Boot Service Logstash Logback Encoder → structured JSON ↓ TCP connection to port 5044 Logstash container TCP input → Elasticsearch output ↓ Elasticsearch Index: togetherlearn-{app}-{YYYY.MM.dd} Example: togetherlearn-user-service-2026.06.30 ↓ Kibana Discover: search ALL services' logs in one query Filter by: service, userId, HTTP status, log level

Sample Log Entry (Structured JSON)

{"@timestamp":"2026-06-30T12:34:56Z", "level":"INFO", "app":"user-service",
"message":"User logged in", "userId":"550e8400-...", "method":"POST",
"path":"/api/auth/login", "status":200, "duration_ms":145}
What to say

"Every service uses the Logstash Logback Encoder to emit structured JSON logs over TCP to Logstash on port 5044. Logstash forwards to Elasticsearch, indexed as togetherlearn-{service}-{date}. Instead of SSH-ing into individual containers and running docker logs, we can search all 10 services' logs in one query — filter by service, by userId, by HTTP status, by error level. In production Kubernetes with hundreds of replicas, this scales to billions of log entries."

That's the power of programming against a standard interface."

We wait for kubectl rollout status to confirm successful deployment before the pipeline completes."

Tough VIVA Q&A — One-Line Answers

QuestionYour Answer
"Why microservices over a monolith?" Each domain deploys, scales, and fails independently. A bug in chat-service doesn't take down course-service. Different services can use different databases optimized for their needs.
"Why RabbitMQ instead of direct REST calls for notifications?" Temporal decoupling — if notification-service is down, events queue and deliver when it recovers. No message is lost, and no producer has to wait. REST would require synchronous retries and tight coupling.
"How do you prevent cascading failures?" Resilience4j circuit breakers at the gateway: 50% failure rate over 10 calls opens the circuit for 30 seconds and immediately returns 503 — stops queuing threads against a degraded upstream.
"How does logout work securely?" The JWT's unique jti claim is written to Redis on logout with the token's remaining TTL. The gateway checks Redis on every request. When the TTL expires, the blacklist entry self-deletes.
"What if Redis goes down?" Rate limiting and profile caching degrade gracefully (fallback to DB). The JWT blacklist check would be the concern — this would be handled by Redis Sentinel or Redis Cluster in production.
"How do services find each other?" Client-side discovery via Netflix Eureka. The gateway resolves lb://SERVICE-NAME to a live IP at request time, not at startup. No hardcoded URLs anywhere.
"Isn't this a distributed monolith?" No — each service has its own database, deploys via separate Docker image, and communicates only via REST API or events (never shared memory or shared DB). They can be deployed and scaled independently.
"How does WebSocket authentication work?" Browsers can't send Authorization headers on WebSocket upgrades, so JWT is passed as ?token= query param. The gateway's JwtAuthFilter handles both the header and query-param cases identically.
"What distributed patterns did you implement?" API Gateway, Client-Side Service Discovery, Circuit Breaker, Database-per-Service, Async Event-Driven, Cache-Aside, Distributed Tracing, JWT Blacklist, Rate Limiting, HPA auto-scaling, Rolling Deployment.
"How do you handle a service that's slow, not down?" The circuit breaker has a timeout (10s) — calls taking longer than 10s count as failures. Once 50% of the sliding window fails or times out, the circuit opens.
"What's the dead-letter queue for?" After 3 retry attempts with 3-second backoff, a failed message goes to tl.notifications.dlq instead of being silently dropped. We can inspect and replay messages from the DLQ manually.
"How do you do zero-downtime deployment?" Kubernetes rolling update: kubectl set image replaces pods one by one. The old pod serves traffic until the new one passes readiness probes. kubectl rollout status confirms completion before the pipeline marks success.
